# 表格抽取评测 v1 分析（P1-11）

> 配套数据：`summary.json`（逐表指标）、`summary.md`（人读表）；标注数据：`data/evaluation/table-eval-v1.json`（149 个单元格）。
> 重跑：`python scripts/evaluate_table_extraction.py --output-dir reports/ranking/table-eval-v2`。

## 1. 这把尺子是什么

把 8 张真实年报表格人工标成单元格三元组（行标签、列头、数值、单位），共 149 个单元格：季度表 2 张（32 cells）、附注收入成本表 2 张（24）、分行业表 2 张（54）、主要会计数据表 2 张（39）。抽取器实现同一接口 `extract_cells(text, table_type)`，输出与标注逐格比对。

| 表型 | 实现 | 正确 / gold | Precision | Recall |
|---|---|---:|---:|---:|

| note_cost | ⬜ 未实现 | 0 / 24 | 0 | 0 |
| segment | ⬜ 未实现 | 0 / 54 | 0 | 0 |
| annual_data | ⬜ 未实现 | 0 / 39 | 0 | 0 |

## 3. 尺子抓到的一个具体 bug

茅台季度表的"归属于上市公司股东的扣除非经常性损益后的净利润"一行 **4 个单元格全错**（该行 0/4），伊利同表全对（4/4）。根因：

- 茅台 PDF 的线性化顺序是「数值在前、标签在后」——扣非净利润的四个值出现在标签**之前**；
- 正则抽取器"标签后取 4 个数字"，于是把下一行（经营活动现金流量净额）的值当成了扣非值；
- 伊利顺序正常（标签在前），所以全对。

这正是 Oracle strict 只有 0.31 的直接证据之一：不是检索找不到，是**表格的行列对应关系在文本化时丢失了**。

## 4. 意义与下一步

- 这张尺子让"表格重建"有了精确的分数起点：v1 全表型正确 28/149（18.8%），B 阶段的目标是把其余 121 个单元格的正确提取实现出来并回归。
- 接口已固定（`src/findoc_rag/table_extraction.py`），未来的坐标重建 / 列头对齐实现只需实现同一接口即可对比。
- 标注边界：assistant 标注、数值人工核对自源 chunk 文本；单元格未覆盖增减率列与"减少 x 个百分点"文本列，后续可扩展。

## 5. 面试讲法

> 表格题答不对时，我先不急着改代码，而是把 8 张真实表格标成单元格三元组（行、列、值），让抽取器输出同样结构逐格比对。尺子一量就定位到具体错误：茅台季度表的扣非净利润标签在数值后面，正则把下一行的现金流数字当成了答案。这个 bug 解释了为什么"证据摆在眼前也只有 0.31 分"——不是检索问题，是表格结构在文本化时丢了。
