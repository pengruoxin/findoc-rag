## 1. 当前完成度

FinDocRAG 是面向中文上市公司年报的可追溯 RAG：PDF → 按结构切片 → 版本化索引 → 检索 → 口径路由 → 带证据门禁的回答，外加一套可复现的双层评测体系。

- **评测基础设施 ✅** 评测集定版、数据集完整性门禁、配置强制落盘、相对时间锚定——评测本身可信、可复现、防泄漏
- **A 阶段检索定论 ✅** 变体矩阵、融合权重扫描、同义词改写、OOV + LLM 改写、中文 dense 对照（2026-08-11 收口）：默认 lexical-only + LLM 查询改写
- **DeepSeek 真实三轨基线 ✅** Oracle 0.9714 / Retrieved 0.5429 / Robustness 0.5455（strict）+ RAGAS，逐题归因已落盘
- **未完成** B 表格重建（坐标几何层已追平文本基线，生成接入待做）、C 行为 / 时间对齐、D 公信力工程、96 变体与 OOV 实例人工审核

一句话现状：**评测工程已经具备竞争力，系统能力（检索、表格、生成）还有明确的、被数据定位的短板**。

## 2. 三个战略问题

### 2.1 语义检索到底该不该用、怎么用

评测揭示的不是"语义模型弱"这么简单：同一个模型在"股票代码 / 简称"这类问法上能到 0.676，在原题和口语问法上只有 0.2 左右。说明**问句的形态**（长度、指代是否唯一）的影响远大于模型本身。

**权重扫描已做完并给出定论**（fusion-sweep-v1）：只用关键词检索、完全不掺语义检索，在三种问法上都碾压任何融合权重（Hit@5 0.838 / 0.811 / 0.730）。逐问法挑最优也全都选"不掺"，说明按问法动态选路在当前模型下没有增益。给语义路任何正权重都是拖累。

**2026-08-11 对照已做完**：换中文专用小模型（bge-small-zh-v1.5）在三种问法和 OOV 上全面退化（dense 0.083–0.568，均低于 E5），证明当前 dense 失败的主因不是"中文/多语言模型能力"，而是问句形态 + 上游表格线性化。同时 OOV 评测证明 **LLM 查询改写是词表外问法的决定性杠杆**（lexical Hit@5 0.194 → 0.694）。剩下的问题：bge-m3 等更大模型在表格结构化之后能否补上语义路，届时用同一套扫描重新验证融合，而不是继续盲调。

**另一个上游因素（已确认）**：PDF 表格线性化（数字与标签分离、行列关系丢失）让语义检索的输入以"数字密集的无结构文本"为主，进一步放大了表面相似度误导（实测语义检索最常召回"关联交易–存款业务"这类无关数字表格）。**决策：暂用关键词检索（已落地），B 阶段表格结构化完成后，与更强语义模型一起用同一套扫描重新验证**——届时模型能力与信息提取质量可以分离归因。

**术语处理三层架构（新 PDF 可扩展性的答案）**：

1. **查询侧**：LLM 查询改写把用户口语归一化为通用财务术语（不依赖具体文档，新 PDF 不需要改）；
2. **文档侧**：指标知识库 + ingest 时 LLM 术语归一化，把不同文档的同一概念（销售收入 / 营业收入）打到同一概念 ID——这是查询改写解决不了的层，因为 LLM 不知道新文档用什么措辞；
3. **快速兜底**：确定性词表只放高频确定改写，不是机制。

验证机制：**OOV（词表外改写）评测**验证查询侧；**document-blind 评测**（未见过的新公司 / 新年度）验证两层组合在真实新文档上有效。单纯靠手工扩词表不是可扩展方案，这条边界已明确写入设计。

### 2.2 表格结构化：生成侧唯一的大杠杆

直接把正确证据摆在眼前也只有 0.31，说明检索不是生成侧的瓶颈。这是硬骨头，但也是把全对率从 0.3 拉到 0.6+ 的唯一路径，同时是最能展示工程深度的部分：单元格坐标重建、列头对齐、跨页表格合并、单位校验。

### 2.3 时间与口径语义：从 demo 到领域产品的分水岭

年报特有的歧义：去年 / 前年（时间锚点在哪）、合并 vs 母公司（口径）、扣非 vs 归母（口径）、已实施 vs 预案（时点）。评测已经证明这些问题真实存在（时间对齐的 bug 已复现）。做好这一层，系统才能回答"什么时候该答、什么时候该追问、什么时候该拒"——这正是 Agent 的核心能力。

## 4. 系统侧待办（非评测）

[改进清单](./evaluation/improvement-list-zh.md) 只覆盖评测集本身。以下是系统链路的待办，按优先级：

**P1**

- **上传只是把文件存下来，没有后续解析和建索引** —— `/v1/uploads` 返回"已上传"之后没有后台处理阶段，UI 上很容易被误解成"上传完就能问了"。需要一个任务状态机、清楚的错误信息，以及把索引版本写回去
- **表格还是拉平成一行文字** —— 见 §2.2。应该保存表格区域、行列坐标、单位和抽取置信度，并给跨页表格建回归样例
- **UI 的证据和调用链展示没有契约测试** —— 前端依赖后端字段名，字段一改就悄悄坏掉。需要用固定的接口返回数据驱动浏览器级冒烟测试，覆盖示例问题、空结果、拒答、上传失败和证据折叠

**P2**

- 索引版本切换和实验对比界面
- 延迟、token 成本、拒答率、跨公司污染率这几个运营指标
- OCR、扫描件、页眉页脚异常的独立质量门禁
- 调用链里敏感查询的脱敏和保留期策略
- README 与实际启动脚本、端口冲突处理、DeepSeek 配置保持一致

> 目标数字是方向性估计，不是承诺；每一格都要通过冻结集配对对比验证之后再更新。

> **RAG 的工程价值定位**：长上下文提高的是"模型一次能消费的信息上限"，RAG 解决的是"哪些信息值得进入上下文"。对大规模企业知识库，把全部文档直接塞给模型既有 token 成本和延迟问题，也会引入无关证据和口径干扰（同一份年报里营业收入、主营业务收入、母公司/合并口径并存）。RAG 本质是 query-aware context compression：筛选最小但充分的证据集，在保持准确率和可追溯性的同时降低 input token 与推理成本。指标已落地：`avg_context_tokens` / `p95_latency_ms` / `avg_evidence_tokens_top5`。

## 6. 已经能讲的故事与最大风险

能讲的（见 [面试说明](./interview/findoc-rag-interview-guide-zh.md)）：

- **评测工程** —— 识别出系统偏关键词检索、96 个专业变体问句、真实年报干扰段落、防泄漏门禁
- **数据驱动归因** —— 用"直接给答案 0.31 vs 真实检索 0.09"定位检索瓶颈；发现语义检索只在股票代码问法上有效这个反常现象
- **工程严谨性** —— 一票否决的门禁、配置快照、迁移清单、防止同题多问法虚高样本量

最大风险，按严重度：

1. **表格没做** —— 被问"季度数字怎么抽的"，目前只能答"拉平成文字 + 正则"，这是最薄的一环
2. **标准答案是自审的** —— 必须补第二人独立复核，才能对外主张准确率
3. **样本量太小** —— 2 家公司 1 个年度，任何数字都要带边界声明
