# FinDocRAG 面试说明

## 一句话介绍

FinDocRAG 是面向中国上市公司年报的结构感知、可追溯 RAG 系统。系统不只返回答案，还记录 PDF 处理过程、证据来自哪个切片、检索用了哪个版本、引用了哪段原文、以及失败的原因，支持离线评测与持续优化。

> 这份文档面向面试场景，会用行业术语。术语的白话解释见 [术语表](../glossary-zh.md)。

## 项目亮点

1. **真实复杂文档**：针对中文年报的多级章节、跨页内容、页眉页脚、脚注和复杂表格设计，不是玩具 QA 数据集。
2. **结构感知切片**：按标题层级、页面元素和长度预算切分，保留章节路径、页码、元素坐标和源元素映射。
3. **检索选型有实验依据**：BM25、multilingual-e5 语义检索、加权 RRF 融合三条路都实现了，并在同一批题上做了权重扫描。**结论是当前纯 BM25 全面胜出，默认策略已改成纯关键词检索**——这个结论本身是个好素材：不是"我上了 hybrid"，而是"我测出 hybrid 在我的数据上是负优化，并说清了为什么"。
4. **元数据路由**：按公司、年份、文档范围先过滤，避免多家公司年报模板相似导致串文档。
5. **证据门禁与拒答**：证据的公司、年份或核心指标与问题不一致时直接拒绝生成，避免大模型在错误证据上编出流畅答案。
6. **回答层可替换**：默认走抽取式和确定性表格抽取；配了 `DEEPSEEK_API_KEY` 之后接 DeepSeek。
7. **可观测**：保存问句、候选结果、最终证据、调用链、处理问题和实验配置，错误能定位到 PDF 解析、切片、召回、重排还是生成。
8. **三条赛道的生成评测**：同一批冻结题分别跑"直接给正确证据""走真实检索""混入干扰"三种上下文；48 题拆成 120 个原子事实，用 53 个真实年报干扰段落测错公司、错期间、错口径、证据不全和因果硬凑。

## 技术路线

```text
年报发现 / 下载 → 来源清单 → PDF 解析成中间表示（带页码坐标）
→ 按结构切片 → 关键词检索（+ 语义检索，当前默认关闭）
→ 公司 / 年份路由 → 证据门禁 → 表格抽取或大模型回答
→ 引用 + 调用链 → 三条赛道评测与失败归因
```

## 面试回答要点

### 为什么不用纯向量检索？

财务问题里全是公司名、年份、会计科目和数字，关键词检索对专有名词和精确匹配更稳；语义检索理论上对换种说法更宽容。所以我把两条路都实现了，在同一批题上做权重扫描来选，而不是凭感觉。

实测结果反直觉：语义检索只在"600519 去年营收"这类短问句上有用（Hit@5 0.676），换成长问句或原文措辞就掉到 0.2 左右。融合反而把关键词检索排在第 1–2 位的正确证据挤到第 6–7 位——因为那些题的语义检索连候选池都没捞到正确证据，只贡献噪声。所以现在默认关掉语义路，等换了更强的中文模型再用同一套扫描重新验证。

### 为什么要做元数据路由？

不同公司的年报有大量同名章节。不按公司和年份过滤，系统可能召回另一家公司的"审计委员会"段落，而大模型照样能生成一个看着合理的答案。实测这个过滤是检索侧最大的单一杠杆（Hit@5 从 0.757 提到 0.838）。路由过滤和证据门禁一起降低这个风险。

### 上下文都这么长了，RAG 还有必要吗？

长上下文和 RAG 不是替代关系。长上下文提高的是模型一次能消费的信息上限，RAG 解决的是哪些信息值得进入上下文。对企业级知识库，把所有文档直接塞进去既有 token 成本和延迟问题，也会引入无关证据和口径干扰——同一份年报里营业收入、主营业务收入、母公司口径和合并口径并存，模型"看得到"不等于知道该依据哪一个。所以我把 RAG 理解为 query-aware context compression：从大规模语料里筛出最小但充分的证据集，在保持准确率和可追溯性的同时降低输入 token 和推理成本。

这不是空话，我的评测现在每个实验都同时报 `avg_context_tokens` 和 `p95_latency_ms`：比如真实检索赛道平均只送约 1.5k token 的上下文就能回答，而整份年报是几万到几十万 token。下一步我准备做 Accuracy–Token Pareto 实验——在严格全对率不下降的前提下压缩上下文，量化"同样质量下少用多少 token"。

### PDF 表格怎么处理？

先建带页码、坐标和元素映射的中间表示，保证覆盖率。后来发现表格被拉平成一行文字之后行列关系就丢了，于是单独记了一条处理问题，并给季度指标加了确定性的行列抽取、单位校验和回归测试。

这也是目前最薄的一环，我会主动说：现在还是"拉平 + 正则取数"，多列和上期/本期并排的表会取错。评测已经把它定位成全链路最大瓶颈——直接把正确证据摆在眼前，全对率也只有 0.31，说明卡的不是检索而是从证据里抽数字。

### 如何证明项目不是 demo？

每次实验固定数据集版本、索引版本和配置三个版本号。检索侧记录 Recall / Precision / MRR / NDCG，生成侧记录事实、单位、引用、行为和语义指标。数据门禁会验证"这个数值确实出现在绑定的原文引用里"，改动前后做逐题配对并列出哪些修好了、哪些退化了，而不是只展示成功案例。

## 90 秒介绍模板

"我做的是 FinDocRAG，一个针对中国上市公司年报的可追溯 RAG。难点不在调大模型，而在中文复杂 PDF 的结构恢复、跨页表格、公司和年份混淆，以及怎么证明答案真的有证据支持。我把 PDF 转成带页码和坐标的中间表示，按结构切片，然后建了关键词、语义和加权融合三条检索路。

有意思的是评测把我的直觉推翻了：融合在我的数据上是负优化，语义检索只在股票代码这类短问句上有用，所以默认策略我改回了纯关键词检索——这个判断有权重扫描的完整数据支撑。

生成评测也不是只看一条答案：48 个问题拆成 120 个原子事实，分别跑'直接给正确证据''走真实检索''混入 53 个真实干扰段落'三条赛道。三条一对比就能定位问题出在解析、切片、召回、口径判断还是生成。每次修改都做逐题配对对比。"

## 当前结果与边界

所有数字见 [评测基线](../evaluation/baseline-zh.md)，其中 §7 是"评测集怎么讲"的完整话术。后续计划与最大风险见 [roadmap](../roadmap-zh.md)。

面试时必须主动说的边界：

- 检索回归集和生成集的标准答案都是助手自审的，没有第二人独立复核
- 只有两家公司、一个年度
- 旧 32 题的 DeepSeek 分数不代表新版 48 题的数据，不能搬过来用
- 指标用于工程迭代，不宣称通用 SOTA

主动说边界比被问出来强。这些限制本身也是可讲的内容——知道自己的数字在什么条件下成立，是工程能力的一部分。
