# Agent hard-v3 P4-C：开放式 Claim 风险路由

## 结论

P4-C 回答的是一个比“再补一条规则”更重要的问题：**错误类型从未见过时，系统怎么决定
要不要升级复核？**

实现没有新增“因果错误”“否定错误”“口径错误”的硬拒答规则，而是计算 claim 与其
requirement、文档范围和引用证据之间的通用语言支持覆盖度。覆盖异常只产生 `review`，由
DeepSeek Verifier 开放式判断证据是否支持；本地规则不能据此直接拒答。

最终结果：

- 未见语义故障的同代码消融：路由 **9/15 → 15/15**，安全处理 **9/15 → 15/15**，
  unsafe accept **6 → 0**；
- 正常组合严格通过保持 **45/48 → 45/48**，没有新增正常模型请求；
- P4-B 已知故障回归保持 **15/15**，细项遗漏修复仍为 5/5；
- CLI 的抽取任务现在默认 `auto`：只有原有高风险任务或开放风险信号命中时才调用独立
  Verifier；仍可显式 `off` 或 `always`；
- 没有增加第三个 Agent，也没有让多个 Agent 自由讨论。

全仓验证结果：**392 passed**；Ruff、组合报告生成与差异空白检查全部通过。

这证明了“未知错误”可以通过**异常发现 → 通用证据审计**处理一部分，但不证明系统能发现
所有未知错误。

## 开放风险信号

对每条 claim：

1. 把中文和拉丁字母规范化；
2. 生成字符二元组；
3. 计算这些二元组在 requirement 主体、事实期间、文档范围和引用 evidence 中的覆盖率；
4. claim 至少有 6 个二元组且覆盖率低于 0.72 时，记录
   `low_evidence_language_coverage`；
5. 状态只能是 `review`，不能因为覆盖率低直接拒答。

0.72 来自当前 calibration + post-hoc dev 的 109 条正常 claim 审计：最低正常覆盖约 0.704；
该阈值会提示 1 条正常 claim，但它本身有 5 个 requirement，原本就会调用 Verifier，因此
不会增加正常请求。这个阈值属于开发结果，仍需冻结集无偏确认。

## 未见故障集

故障设计刻意不修改本地硬规则已经覆盖的公司、显式年份、数字、单位或引用文档范围：

- `semantic_negation`：在正确事实后加入与事实相反的否定；
- `unsupported_causal_inference`：加入证据没有的必然因果和未来影响；
- `scope_qualifier_corruption`：加入证据没有的境外零售业务范围限定。

5 条存量正常轨迹各注入三类故障，共 15 条。其中两条原任务只有 3 个 requirement，P4-B
会留在单 Agent 快路径；另外三条原本就是高风险任务。

### 同代码消融

两组使用相同数据、代码、Verifier prompt、DeepSeek 模型和评测器，只切换开放风险信号：

| 指标 | 信号关闭 | 信号开启 | 变化 |
|---|---:|---:|---:|
| 路由到 Verifier | 9/15 | **15/15** | +6 |
| 安全处理 | 9/15 | **15/15** | +6 |
| 错误放行 | 6/15 | **0/15** | -6 |
| Verifier 结构错误 | 0 | 0 | 0 |
| 模型请求 | 9 | 15 | +6 |
| token | 38,529 | 59,914 | +21,385（+55.51%） |

三种故障均由 3/5 提升到 5/5。增加的成本只发生在原本未路由的 6 个故障样本上，不代表
正常线上请求会同比增加 55.51%。

## 正常答案与已知故障回归

| 正常范围 | P4-B | P4-C | P4-C Verifier 请求 | P4-C token |
|---|---:|---:|---:|---:|
| calibration | 22/24 | 22/24 | 10 | 45,078 |
| dev（post-hoc） | 23/24 | 23/24 | 8 | 36,734 |
| 合计 | **45/48** | **45/48** | **18** | **81,812** |

P4-B 正常成本为 80,560 token；P4-C 增加 1,252（1.55%），来自更明确的 Verifier prompt
和远程输出长度，模型请求仍是 18，没有因新信号新增正常调用。

原有 15 个主体、数字和细项遗漏故障仍安全处理 15/15；请求仍为 20，token
80,882 → 81,627（+745，+0.92%）。主体错误仍有 5/5 在模型调用前本地拦截，细项遗漏
仍有 5/5 完成一次修复并通过二次复核。

## 自动路由策略

抽取 CLI 支持三种策略：

- `auto`（默认）：审计事项、至少 4 个 requirement，或开放风险信号命中时复核；
- `off`：完全关闭独立 Verifier，保留主 Agent 和本地确定性门禁；
- `always`：每个成功抽取答案都复核，用于特殊审计或对照实验。

旧的 `--evidence-verifier` 仍兼容，等价于启用条件路由。普通查询不默认使用多个 Agent，
默认变化只是高风险抽取不再要求操作者记住额外开关。

## 负实验

第一次未见故障实验保留：P4-B 路由 9/15，严格成功识别 7/15，另有 2 个非法
`incomplete` 结构安全关闭；P4-C 第一轮为 14/15。失败样本的注入语句包含“母公司”，而
原证据本身多次出现“归属于母公司股东”，存在语义歧义。

最终 v2 把范围故障改为证据明确没有的“境外零售业务口径”，并增加同代码关闭信号的
消融开关。两组结构错误均为 0。旧报告不进入最终能力数字，但保留用于说明评测样本本身
也需要反证和修订。

## 限制

- 字符覆盖异常不是语义蕴含；使用大量证据原词但悄悄改变关系的错误仍可能得高覆盖；
- DeepSeek Verifier 也可能误判，因此 15/15 不能外推为任意未知错误 100%；
- 15 个故障是受控合成，样本小；正常阈值又使用了 post-hoc dev；
- 主 Agent 与 Verifier 仍是同 provider/model，只实现上下文和职责隔离；
- frozen test 始终封存，没有无偏确认；
- 高风险金融场景仍应保留人工升级，而不是把风险分数包装成事实置信度。

下一步不应继续加风险词。优先顺序是：冻结当前阈值和 prompt，补一组不依赖低语言覆盖的
关系偷换/OCR 符号退化盲测；如果仍稳定，再一次性打开 frozen test。只有跨层冲突确实
需要并行专长时，才考虑新的专用 Agent。
