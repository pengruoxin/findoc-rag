# 术语处理方案：同义词可扩展性设计

> 要回答的问题：**以后来了新 PDF（新公司、新年度、新行业），系统怎么保证还能处理用户的各种说法？** 不能靠"每遇到一个新说法就加一条词表"。

## 1. 问题定义

检索失败的一大来源是"用户说法 ≠ 年报措辞"：

- 用户说"赚了多少"，年报写"营业收入"；
- 用户说"毛利水平"，年报写"毛利率"；
- 新公司年报可能写"销售收入""销售总额"，而不是"营业收入"；
- 新行业（银行：不良贷款率；保险：综合偿付能力充足率）带来完全没有收录的术语。

问题分两个维度：

| 维度 | 例子 | 本质 | 谁解决 |
|---|---|---|---|
| **查询侧**：用户怎么问 | "赚了多少""每卖一百块能剩下多少" | 说法无限变化 | LLM 查询改写 |
| **文档侧**：新文档怎么写 | "销售收入" vs "营业收入"；银行"不良贷款率" | 措辞与概念不一致、概念集合扩展 | 指标知识库 + ingest 归一化 |

确定性词表只能覆盖"已见过的改写"，两个维度都覆盖不了——它不是机制，是缓存。

## 2. 设计目标

1. 用户侧长尾说法不靠手工词表（模型能力覆盖）；
2. 新文档的措辞差异不靠手工词表（文档侧归一化）；
3. 每一步都可评测、可回归、可解释；
4. 面试能讲清楚边界和进化路线。

## 3. 三层架构

| 层 | 机制 | 解决什么 | 新 PDF 进来时要改吗 |
|---|---|---|---|
| ① 查询侧 | LLM 查询改写：口语 / 简称 → 通用财务术语 | 用户说法变化 | 不需要 |
| ② 文档侧 | 指标知识库（概念 ID + 别名 + 公式）+ ingest 时术语归一化 | 文档措辞差异、新概念 | 半自动：新术语走"抽取候选 → 对齐概念 → 评测驱动确认" |
| ③ 快速兜底 | 确定性词表（只放高频确定改写） | 已知改写的零成本快速通道 | 只加最确定的，不是机制 |

### 3.1 查询侧：LLM 查询改写

输入：用户查询（相对时间已解析）。
输出：归一化后的查询（如"去年赚了多少"→"2024年营业收入是多少"）。

设计要点：

- 不依赖具体文档，只做"口语 → 通用财务术语"，所以新 PDF 不需要改；
- 失败 / 不可用时回退到确定性词表，链路不挂；
- 相同查询结果缓存，避免重复调用；
- 触发策略（待拍板）：全部查询都改写（简单但多一次调用）或"确定性词表未命中 + 检索分数低"时才触发（省成本，复杂）；
- 风险：LLM 可能改写错（引入错误术语、改掉口径），需要 prompt 约束 + 评测把关。

### 3.2 文档侧：指标知识库 + ingest 术语归一化

这是查询改写解决不了的层：LLM 不知道新文档里用的是哪个词，所以**文档侧的措辞要先归一到概念**。

核心：**指标知识库（概念层）**

```yaml
metric:
  id: revenue
  name: 营业收入
  aliases: [营业收入, 销售收入, 销售总额, 营业总收入, 营收]
  formula: SUM(orders.pay_amount)
  base_table: orders
  dependencies: [orders.pay_amount, orders.paid_at]
```

新文档 ingest 流程：

```text
新 PDF → 解析 → LLM 抽取候选财务术语 → 与知识库概念对齐
      → 命中：给 chunk 打概念标签 / 加入术语别名索引
      → 未命中：登记为新概念候选（人工/评测确认后入知识库）
```

归一化落点（二选一，待拍板）：

- **A. 索引侧概念标签**：chunk 打上概念 ID 标签，查询改写出的标准词能通过标签命中"销售收入"的 chunk（改索引，需重建）；
- **B. 检索时概念扩展**：查询侧标准词 + 知识库别名在检索时展开（不改索引，与现在的查询改写同路径，可先做）。

### 3.3 快速兜底

确定性词表保留，但明确它是"已知高频改写的缓存"，不是能力来源。

## 3.4 三层关系：缓存 → 过渡 → 终局

两个常见追问必须先讲清楚：

**"词表是不是还是会慢慢更新？"**——会，但地位变了。覆盖靠模型（LLM 改写 / dense），词表只缓存最高频确定的改写。它会积累，但即使永远不更新，长尾说法依然能处理。词表是自定义短语，不是输入法。

**"dense 不才是同义词的正解吗？"**——是。向量空间里意思相近的词本来就该距离近，dense 就是为此设计的。但评测证明**当前模型在这个语料上没做到**（semantic Hit@5 只有 0.16，被数字密集表格的表面特征带偏），原因是模型弱 + 表格输入未结构化。所以现在的顺序是：LLM 改写先覆盖用户措辞（不依赖词表），同时修表格输入、换更强模型，让 dense 重新承担语义主力；届时 LLM 改写退居查询理解层。

```text
缓存（词表）   高频确定改写，零成本快速通道，会积累但不是机制
   ↑
过渡（LLM 改写） 模型能力做术语归一化，不依赖词表，覆盖用户长尾说法
   ↑
终局（dense）  向量语义匹配"意思相近"，前提：表格结构化 + 更强中文模型
```

## 4. 评测验证（证明方案真的可扩展）

三个档位，分开报告：

| 档位 | 测什么 | 数据来源 |
|---|---|---|
| **IV（词表内）** | 已知改写是否仍命中 | 现有 semantic 变体 |
| **OOV（词表外）** | 没见过的说法是否靠 LLM 改写救回 | LLM / 真人生成口语变体（已生成 36 条雏形） |
| **document-blind** | 完全没见过的公司 / 年度是否有效 | P3 新增文档，整份留出 |

关键指标：Hit@5 在 IV / OOV / blind 三档分别报告。OOV 低 → 证明系统能力是词表给的；OOV 高 → 证明语义归一化真实有效。

## 5. 实施路径

| 阶段 | 内容 | 验收 |
|---|---|---|
| **0. dense 对照实验（先消除重复风险）** | 不重建索引，用中文专用向量模型（如 bge-small-zh-v1.5）在现有 chunk 上编码，OOV 集对比 E5 与 LLM 改写 | 回答"更强的 dense 在现有输入上能不能跨过同义词"；决定砍掉 / 保留 / 组合查询改写层 |
| **1. 查询侧 MVP** | LLM 改写器接入评测；OOV 集跑对比（无改写 vs LLM 改写） | OOV Hit@5 显著提升；IV 不退化；0 回归 |
| **2. 文档侧 MVP** | 指标知识库 schema（先覆盖现有 12 个指标）；检索时概念别名扩展 | "销售收入"类同概念措辞能命中同一 gold |
| **3. 盲测** | 新公司 / 新年度 ingest + document-blind | blind 档 Hit@5 ≥ OOV 档的 80% 视为通过 |
| **4. 收口** | 触发策略调优（低置信才改写）、成本/延迟记录、生产集成 | 成本-质量 Pareto 数据 |

**为什么先做阶段 0**：查询改写与 dense 在"措辞归一化"上存在重叠区。与其默认两套都做，不如先花小钱验证"更强的 dense 在现有输入上够不够"：

- dense 已够 → 砍掉大部分改写层，专注表格结构化（dense 的输入问题）；
- dense 仍弱 → 证明瓶颈在输入 / 模型，LLM 改写作为过渡有价值；
- 两者各有短板 → 组合：LLM 改写做查询理解、dense 做语义匹配、词表当缓存。

用评测消除重复风险，而不是拍脑袋选路线。

## 6. 成本与风险

| 风险 | 缓解 |
|---|---|
| LLM 改写延迟 / 成本 | 缓存；只在低置信触发（阶段 4）；记录 p95 |
| LLM 改写引入噪声 | prompt 约束"只做术语归一化，不添加信息"；OOV/IV 回归门禁 |
| 知识库维护漂移 | 概念 ID 版本化；评测驱动增补（失败案例 → 候选 → 确认） |
| 词表过拟合评测 | IV / OOV 分档报告；OOV 由 LLM / 真人生成，不来自规则模板 |

## 7. 面试讲法

> 同义词问题要分两层看：用户怎么说（查询侧）和文档怎么写（文档侧）。查询侧我用 LLM 做术语归一化，不依赖词表，所以新 PDF 不需要改；文档侧靠指标知识库把不同措辞归一到同一概念，新术语走半自动登记。验证上我用三类评测：词表内改写、词表外改写、整份文档盲测——如果没见过的说法和没见过的文档都能命中，才算真的可扩展，而不是背词表。

追问应对：

- "LLM 改写会不会很贵？"——有缓存，而且只在确定性词表没覆盖、检索置信度低时触发，最后有成本-质量数据。
- "新行业的术语知识库不也得扩展？"——是的，但这是结构化的概念登记（版本化、可审计、评测驱动），不是"每句话加一条词表"；而且盲测会告诉我们哪些概念还没覆盖。
